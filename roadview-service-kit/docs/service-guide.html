로드뷰 서비스 적용 가이드

모의 프로젝트(roadview-mock)에서 실제 서비스로 가져갈 것만 추린 문서다. 무엇을 그대로 쓰고, 무엇을 바꿔야 하며, 적용할 때 무엇을 먼저 결정해야 하는지를 다룬다.

근거는 세 가지로 구분해 적었다.

  • 검증 모의 프로젝트에서 직접 돌려 확인한 것
  • 보고서 처음에 받은 조사 보고서 2건에 적힌 내용. 이 문서에서 다시 확인하지 않았다
  • 미검증 모의에서 확인하지 못해 실서비스 전에 반드시 시험해야 하는 것

1. 한눈에 보기

모의 프로젝트는 화면과 흐름을 검증한 것이고, 데이터 평면은 전부 가짜다. 서버, DB, 타일, 블러 모델은 없다.

구분 내용
그대로 가져갈 수 있는 것 키프레임 선택 로직(순수 함수), 뷰어의 조작·내비게이션·신고 흐름, 지도–뷰어 동기화 패턴, 백오피스의 작업 흐름과 화면 구성, API 계약의 형태
반드시 새로 만들어야 하는 것 저장소와 업로드 API, 공간 DB, 타일 생성과 CDN, 얼굴·번호판 블러, 위치·방향 추출, 인증과 권한, 신고 처리 백엔드
버려야 하는 것 가상 도시 모델, 합성 파노라마 렌더러, 브라우저 IndexedDB 저장

가장 먼저 정할 것은 다음 네 가지다. 이 답에 따라 아래 내용의 절반이 달라진다.

  1. 촬영 장비: 360° 카메라인가, 일반 폰·대시캠인가. 일반 사진은 구 전체를 채우지 못해 로드뷰가 아니라 "방향이 있는 사진"이 된다.
  2. 위치 정보의 출처: 사진·영상에 GPS가 들어 있는가. 없으면 지금처럼 사람이 도로와 시작 지점을 고르는 방식만 가능하다.
  3. 공개 범위: 외부에 공개하는가, 내부용인가. 공개라면 블러와 신고 처리가 출시 조건이 된다.
  4. 규모: 도로 길이와 촬영 간격. 저장량과 처리량을 거의 선형으로 결정한다 보고서.

3. 백엔드 API 계약

모의의 함수가 실서비스에서 어떤 엔드포인트가 되는지 정리했다. 응답 형태는 RV.getManifest()가 돌려주는 JSON을 기준으로 삼으면 된다.

모의 함수 실서비스 비고
findNearest(lat, lon, radiusM, {year}) GET /panoramas/nearest PostGIS ST_DWithin + 거리순 정렬 보고서. 모의는 전수 탐색이다
getManifest(id, year) GET /panoramas/{id} 위치, 자세, 타일 경로, 링크, 프라이버시 상태
node.links manifest 안의 links step(인접)과 jump(원거리)를 구분해 둔 구조는 유지
coverage() 커버리지 벡터 타일 모의는 선 6개라 통째로 내려준다. 실제 규모에서는 벡터 타일이어야 한다 보고서
reportBlur(...) POST /reports 모의는 즉시 가림을 추가한다. 실제로는 검수 큐를 거친다
photos.add(...) 업로드 API 6절 참고

적용 시 고려사항:

  • ID를 두 겹으로 둔다. 모의는 위치(nodeId)와 촬영분(nodeId + year)을 구분한다. 실서비스도 "장소"와 "그 장소의 특정 촬영"을 다른 키로 두어야 과거 사진과 재촬영을 다룰 수 있다.
  • 타일 URL에 revision을 넣는다. 모의의 tiles.template이 /tiles/{id}/{revision}/... 형태인 이유다. 재블러가 일어나면 revision만 올리고 CDN 캐시를 강제로 비우지 않아도 된다 보고서.
  • 연도 대체 규칙을 API에서 정한다. 모의의 resolveYear는 요청한 연도가 없으면 가장 가까운 연도를 돌려주고, 화면은 "요청한 연도가 아님"을 표시한다. 이 대체를 서버가 할지 클라이언트가 할지 정하고, 응답에 요청 연도와 실제 연도를 둘 다 담는다.
  • 교차로 노드 정책을 정한다. 모의에서는 교차하는 두 도로가 같은 좌표에 노드를 각각 갖는다. 그래서 한 걸음 갔다 돌아오면 같은 자리의 다른 노드에 서고, 볼 수 있는 연도가 달라진다 검증. 교차로 노드를 하나로 합칠지, 지금처럼 둘지 결정해야 한다.

4. 영상에서 사진 뽑기

모의에서 가장 많이 다듬은 부분이고, 로직은 그대로 가져갈 수 있다.

지금 동작하는 방식 검증

  1. 영상을 일정 간격으로 훑어 프레임마다 선명도(라플라시안 분산)와 움직임(약 0.6초 떨어진 앞뒤 프레임과의 차이)을 잰다.
  2. 움직임이 기준보다 작으면 정차로 보고 후보에서 뺀다.
  3. 정차 구간을 뺀 "주행 시간"을 N초 단위로 자르고, 구간마다 가장 선명한 프레임을 고른다. 직전에 고른 프레임과 반 구간 이상 떨어져야 한다.
  4. 고른 프레임을 도로의 노드에 순서대로 배정한다.

샘플 영상(25.6초, 중간에 3.2초 정차, 1.6초 흐린 구간)으로 확인한 결과:

항목 결과
정차 구간 프레임을 정차로 판별 12 / 12
주행 구간을 정차로 오판 0 / 90
정차 구간에서 뽑힌 프레임 0장
흐린 구간 구간이 간격보다 짧으면 건너뛰고, 길면 그 안에서 덜 흐린 것을 고른다

실서비스에서 바꿔야 하는 것

  • 시간이 아니라 거리로 뽑는다. 지금 방식은 "달리는 동안 속도가 일정하다"고 가정한다. 완전 정차는 걸러내지만 서행은 걸러내지 못해, 느리게 지나간 곳은 사진이 촘촘해진다 검증. 영상에 GPS 트랙이 있으면(GoPro GPMF, CAMM, 별도 GPX) 거리 기준으로 구간을 자르고, 선명도 채점은 구간 안에서 고르는 용도로만 쓴다. mapillary_tools가 이런 텔레메트리 처리와 프레임 샘플링을 제공한다 보고서.
  • 기준값을 실제 영상으로 다시 잡는다. 정차 기준(1.2)과 비교 간격(0.6초)은 합성 영상에 맞춘 값이다. 360° 영상은 하늘과 차량 지붕이 화면의 큰 부분을 차지하고 변하지 않아, 주행 중에도 움직임 값이 작게 나온다 검증. 지평선 부근 띠만 잘라 비교하는 방식을 검토한다.
  • 분석을 서버로 옮긴다. 모의는 브라우저가 영상을 직접 디코딩한다. 폰에서 찍은 HEVC/MOV와 수 분 이상의 영상은 시험하지 않았다 미검증. 실서비스는 업로드 후 서버 작업으로 돌리고, 백오피스는 결과만 받아 검수한다.
  • 간격 모드는 노드와 어긋날 수 있다. 프레임을 노드에 차례로 배정하므로, 추출 간격이 "노드 하나를 지나는 시간"과 다르면 뒤로 갈수록 밀린다 검증. GPS가 있으면 이 문제가 사라진다. 없으면 "지점 수에 맞추기" 모드를 기본으로 둔다.
  • 검수 화면은 유지한다. 자동 선택이 완벽하지 않으므로, 한 장씩 넘겨 보며 제외하는 훑어보기 단계가 실제로 필요하다. 제외해도 뒤 프레임을 당기지 않는 규칙도 유지한다.

5. 뷰어

유지할 것

  • 드래그·휠·키보드 조작, 바닥 화살표 이동, 50m 점프, 크로스페이드 전환
  • 저해상도를 먼저 보여 주고 고해상도로 바꾸는 순서, 시선 방향의 다음 지점을 미리 받아 두는 prefetch
  • 신고 모드: 버튼 → 화면의 한 점 클릭 → 그 방향(heading, pitch)으로 신고 접수
  • 지도 마커가 위치·방향·시야각을 따라가는 동기화

바꿀 것

  • 이미지 한 장을 통째로 텍스처에 올리지 않는다. 모의는 3072px 캔버스를 그대로 쓴다. 폭 4096px를 넘는 텍스처는 일부 기기에서 지원되지 않으므로, 고해상도는 큐브맵 멀티해상도 타일로 간다 보고서.
  • 직접 만든 뷰어를 계속 쓸지 결정한다. 모의 뷰어는 three.js로 직접 만든 400줄 정도의 코드다. 타일 스트리밍까지 직접 구현할지, Photo Sphere Viewer나 Pannellum 같은 기존 뷰어로 옮길지 판단해야 한다 보고서. 모의 뷰어는 화면 요구사항을 정리한 명세로 쓰는 편이 안전하다.
  • 전환 품질. 지점 간 전환은 단순 크로스페이드다. 깊이 정보가 없으면 그 이상은 어렵다 보고서.
  • 실제 입력 장치 시험. 실제 마우스 드래그, 휠, 터치, 키보드 포커스는 자동화로만 확인했고 사람이 만져 보지 않았다 미검증.

6. 사진 업로드와 백오피스

유지할 것

  • 작업을 세 갈래로 나눈 구성: 낱장 등록, 주행 순서대로 연속 등록, 영상에서 추출
  • 등록 전에 "어느 사진이 어느 지점에 들어가는지"를 표로 보여 주고, 교체되는 지점과 남는 사진을 경고하는 단계
  • 등록 현황 지도와 도로별 등록률

바꿀 것

  • 저장소. 지금은 브라우저 IndexedDB라 그 브라우저에서만 보인다. 오브젝트 스토리지 + 메타데이터 DB로 바꾼다. 대용량 영상은 이어 올리기가 되는 업로드 방식이 필요하다.
  • 위치와 방향을 파일에서 읽는다. 모의는 사람이 도로·방향·시작 지점을 고르고, 360° 사진의 가운데가 진행 방향이라고 가정한다. 실제로는 EXIF GPS와 촬영 시각, GPano XMP의 heading을 읽어 자동 배정하고 보고서, 사람은 결과만 고친다. 이 가정이 틀리면 모든 사진이 옆을 본다.
  • 촬영 시각이 촬영분을 정한다. 모의는 기존 연도(2023·2025·2026) 중 하나에만 넣을 수 있다. 실제로는 사진의 촬영 시각으로 새 촬영분이 만들어져야 한다.
  • 중복 방지. 같은 백업을 두 번 가져오면 일반 사진이 중복 등록된다 검증. 파일 체크섬으로 같은 파일을 걸러낸다.
  • 일반 사진의 한계. 일반 사진은 렌즈 보정 없이 해당 방향에 붙여 넣기만 한다. 화각도 사람이 입력한다(기본 65°). 서비스에서는 360° 사진만 로드뷰로 쓰고, 일반 사진은 별도의 "현장 사진" 레이어로 분리하는 편이 낫다.
  • 인증과 권한. 모의 백오피스에는 로그인이 없다. 등록·삭제·전체 삭제에 권한과 감사 기록을 붙인다.
  • 폰 사용성. 420px 폭 레이아웃은 확인했지만 실제 폰 카메라 촬영과 드래그&드롭은 시험하지 않았다 미검증.

7. 개인정보와 법규

이 절은 조사 보고서의 내용을 옮긴 것이다. 출시 전에 법률 검토가 필요하다.

  • 블러는 공개 저장소로 넘어가기 전의 관문이다. 모의는 올린 사진을 그대로 보여 준다. 실서비스에서는 얼굴·번호판 블러를 통과한 이미지만 공개 영역에 저장한다 보고서.
  • 모의의 프라이버시 상태 표시는 가짜다. manifest의 privacy.faces / plates가 누락이 있어도 항상 BLURRED로 나온다 검증. 실제로는 검출 결과, 신고 접수, 재처리 여부를 반영하는 상태값이어야 한다.
  • 신고는 모든 해상도에 반영한다. 모의는 신고 즉시 그 촬영분의 캐시를 지우고 다시 그린다. 실제로는 모든 타일 레벨을 다시 만들고 revision을 올린다. 누락 신고 → 수동 블러 흐름은 자동 블러가 있어도 필요하다 보고서.
  • 신고 내역 저장. 모의는 메모리에만 있어 새로 고치면 사라진다.
  • 한국에서 촬영한다면. 개인정보보호법 제25조의2(이동형 영상정보처리기기)에 따라 촬영 사실 표시와 거부 의사 존중이 필요하고, 군사·보안시설 가림 정책도 필요하다 보고서.
  • 원본 보관. 블러 전 원본을 남긴다면 공개 영역과 분리하고, 접근 기록과 보존 기한을 둔다 보고서.

8. 규모와 비용

모의는 노드 174개짜리라 규모 문제를 전혀 겪지 않았다. 아래는 보고서의 계산식이다.

파노라마 수 = 도로 길이(km) × 1,000 ÷ 촬영 간격(m)
저장량     = 파노라마 수 × 장당 용량 × 보관 시점 수 × 복제 수
  • 촬영 간격을 반으로 줄이면 장수가 두 배가 된다. 저장량을 좌우하는 것은 코덱이 아니라 촬영 간격, 해상도, 보관하는 시점 수다 보고서.
  • 공개 데이터셋 사례에서 360° 이미지 한 장이 약 18.6MiB였다 보고서. 모의 샘플(2048×1024 JPEG, 장당 약 150KB)과는 자릿수가 다르다.
  • 이미지는 API 서버를 거치지 않고 스토리지와 CDN에서 바로 내려간다. 메타데이터와 이미지 경로를 분리한다 보고서.

9. 적용 순서

각 단계가 끝나면 혼자 돌아가는 결과물이 남도록 잡았다.

단계 할 일 끝났다는 기준
1. 결정 1절의 네 가지를 정한다. 뷰어 시안 A·B·C 중 하나를 고른다 장비, GPS 유무, 공개 범위, 대상 구간이 문서로 남는다
2. 실촬영 시험 1~2km를 실제 장비로 찍어 백오피스에 올려 본다 실제 영상에서 정차 판별과 선명도 기준이 맞는지 수치로 확인된다
3. 저장과 API 스토리지, DB, 3절의 API를 만들고 photo-store.js 내부를 교체한다 다른 브라우저에서도 등록한 사진이 보인다
4. 블러 관문 블러 처리를 등록 경로에 넣는다 블러를 거치지 않은 이미지가 공개 경로로 나갈 방법이 없다
5. 타일과 뷰어 타일 생성, CDN, 뷰어의 이미지 로더 교체 고해상도 이미지가 폰에서 끊기지 않고 뜬다
6. 운영 신고 큐, 권한, 감사 기록, 재촬영 주기 신고가 접수부터 반영까지 추적된다

2단계를 3단계보다 먼저 두었다. 기준값과 장비 문제는 실제 영상을 넣어 봐야 드러나고, 지금 백오피스로 서버 없이 시험할 수 있기 때문이다.

10. 출시 전 확인 목록

모의에서 확인하지 못했거나 알고도 남겨 둔 항목이다.

  • 실제 폰 카메라로 촬영해 올리기, 터치 조작
  • 드래그&드롭 업로드
  • 폰 영상 코덱(HEVC, MOV)과 수 분 이상의 긴 영상
  • 영상 분석 중단 버튼
  • 실제 마우스·휠·키보드로 뷰어 조작
  • Chrome 외 브라우저. Safari는 파일로 열었을 때의 저장 동작이 다를 수 있다
  • 실제 GPU. 자동 검증은 소프트웨어 렌더러에서만 돌렸다
  • 정차 기준값과 비교 간격을 실제 영상으로 재조정
  • 서행 구간의 사진 간격 문제 (GPS 기반 추출로 해결)
  • 교차로 노드 정책
  • manifest의 프라이버시 상태를 실제 값으로
  • 가져오기 중복 방지
  • 백오피스 인증과 권한
